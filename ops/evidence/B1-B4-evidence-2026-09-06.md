## 2 · What was missing, and what was built

The stated reasons B1–B4 could not run were all about production: B1 and B2's arms
write and the gate will not open a write probe on production; B3 needs a caller, not a
catalogue; B4 needs live render credentials; and production has one user, who is an
approver, so B1 had nobody to refuse.

None of those is about staging, which has carried two synthetic dealerships since
3 September. **The gap was that no caller existed.** Staging held nine `auth.users`
rows for the fixture staff — and every one of them had `encrypted_password` NULL and no
`auth.identities` row, so **nobody could sign in as any of them.**

### 2.2 The gate lane

A new section in `QUALITY_GATE.mjs`, ahead of B1: **the signed-in caller.** It calls
GoTrue's password grant, holds the token, and makes every later call as an ordinary
REST client with `apikey` and `Authorization: Bearer` — the two headers the dashboard
sends. **No `set_config('request.jwt.claims')`, no `set_config('role')`, no Postgres
role held by the gate.** That is the whole point: the psql arms already in the file
reach Postgres the way PostgREST *presents* a JWT, which is not a signed JWT that
travelled through PostgREST, and that is the line
`two-tenant-proof-2026-09-06.md` §8.4 stops at.

The psql arms were **not removed and not weakened**. Both transports run when both are
configured, and a defect found by either is a FAIL.

New environment variables, all documented in the file's own header:

```
NEXUS_STAGING_REST_URL          NEXUS_STAGING_ANON_KEY
NEXUS_STAGING_APPROVER_EMAIL    / _PASSWORD
NEXUS_STAGING_APPROVER2_EMAIL   / _PASSWORD
NEXUS_STAGING_NONAPPROVER_EMAIL / _PASSWORD
NEXUS_STAGING_OTHER_EMAIL       / _PASSWORD
```

With none of them set, the gate reports **NOT RUN naming every missing variable and
what each identity is for** — verified by running it that way before running it with
them.

### 2.3 Four locks before a single write

B1 and B2 write, and over HTTP there is no `ROLLBACK`. Four things must hold at once:

1. `NEXUS_STAGING_REST_URL` is set **by name**. The variable that may point at
   production is `NEXUS_LIVE_URL`, and the write arms never read it.
2. Its Supabase **project ref** differs from `NEXUS_DB_URL`'s and `NEXUS_LIVE_URL`'s.
   Two spellings of one project are refused.
3. Every identity signs in. Production has one user; these credentials cannot exist
   there.
4. **Measured, not configured:** the "other dealership" account must resolve —
   through `action_approver_context()`, as itself — to a **different** dealership from
   the approver. A single-dealership database cannot satisfy this, and production is a
   single-dealership database. This is the lock that does not depend on somebody
   naming a variable correctly.

## 6 · B4 — still NOT RUN, and now for a measured reason

B4 needs a browser. **The headless browser this gate drives cannot reach
`*.supabase.co` from this container at all**, while the gate's own process reaches the
same host over the same TLS without trouble. Measured, from the browser's own network
events:

```
the gate process   read 10 units from rpc/sentinel_inventory_actions — fine
the browser        1 request to https://wwspuxrbiyagnrnzgate.supabase.co
                   0 responses
                   POST /auth/v1/token — net::ERR_CONNECTION_RESET
```

The session's egress proxy cuts chromium's TLS handshake every time (`ws_closed_mid_
exchange`, ~1.8 kB sent, 39 B received) while `curl` to the same host succeeds. That is
where the gate is running, not what the product does.

**Two defects in B4 itself were found and fixed on the way, and both were the gate
lying about the product:**

- **It reported FAIL.** With no session it emitted *"N of N units do not appear on the
  Inventory screen"* about a screen that had never rendered — a launch-critical red
  line, generated by a check that had not run. It now counts the browser's own
  requests to the project: **zero responses and at least one failed request, with the
  app not signed in, is NOT RUN with the failure text quoted** — anything else stays a
  FAIL.
- **Its session was fabricated and did not work.** It hand-built a session object into
  supabase-js's storage key. supabase-js 2.110 does not accept it — measured: zero
  network requests, `boot()` fell straight through to the login card. And the
  fabricated user carried **no `email`**, while `app.js` `boot()` reads
  `SESSION.user.email` to find the staff row, so even an accepted session would have
  been one no real sign-in produces. B4 now **types the password into the app's own
  login form** when it has one, which is the path a dealership uses; the injection
  survives only for `NEXUS_LIVE_ACCESS_TOKEN`, and is reported as the weaker route.
- A third, smaller one: the harness waited a fixed 6 s and read *"Signing in…"* as
  *"did not sign in"*. A sign-in that this egress is going to reset takes **longer to
  fail than to succeed**. It now waits on an outcome, not a stopwatch.

So B4 is closer to runnable than it was — it needs a machine whose browser can reach
the Supabase project, and nothing else.

## 8 · What was left on staging, and how to remove it

Everything created by the exploratory runs was **deleted**, and the counts returned
exactly to the pre-pass state recorded in `two-tenant-proof-2026-09-06.md` §1
(`audit_log` 4, `inventory_action_events` 5, `inventory` 3, `inventory_actions` 2).
Then the final gate run created its own fixture, which is what remains:

| what | id |
|---|---|
| inventory unit on Alpha | `GATE-PROBE-1788673708220` (400 days in stock, AED 100,000 list / AED 95,000 cost → engine recommends WHOLESALE) |
| action | `e9492201-6c45-4858-965c-67b82f6700b1`, status **APPROVED** |
| `inventory_action_events` | 6 |
| `audit_log` | 5 |

Totals on staging now: inventory 4 (Alpha 3, Bravo 1), inventory_actions 3, audit_log
9, inventory_action_events 11.

**A completed gate run leaves one unit and one action**, and that is the product's own
rule rather than untidiness: `action_propose()` treats an APPROVED action as still
open, so its unit cannot be re-proposed, and cancelling it instead starts a
14-day `reproposal_cooldown_days`. An **interrupted** run leaves a PROPOSED action, and
the next run re-uses it rather than adding another.

**Removal — one statement set, printed by the gate itself in B1's evidence:**

```sql
delete from public.inventory_action_events
 where action_id in (select id from public.inventory_actions where unit_id like 'GATE-PROBE-%');
delete from public.audit_log where summary like '%unit GATE-PROBE-%';
delete from public.inventory_actions where unit_id like 'GATE-PROBE-%';
delete from public.inventory where id like 'GATE-PROBE-%';
```

`audit_log` carries **no `action_id` column** — `action_write_audit()` puts the unit id
in `summary`, and that string is the only handle on those rows. (The first version of
this cleanup statement used `action_id` and would have errored; it was corrected after
reading the table.)

**To remove the sign-in fixtures as well** (this un-does §2.1 and makes B1–B3
un-runnable again):

```sql
delete from auth.identities where email like '%@alpha.staging.invalid' or email like '%@bravo.staging.invalid';
update auth.users set encrypted_password = null
 where email in ('owner@alpha.staging.invalid','manager@alpha.staging.invalid','member@alpha.staging.invalid',
                 'owner@bravo.staging.invalid','member@bravo.staging.invalid');
```

Nothing was written to production. No git command was run. The n8n box was not
contacted.
