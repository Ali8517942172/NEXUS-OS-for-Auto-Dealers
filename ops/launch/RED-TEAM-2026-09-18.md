# RED-TEAM — the ingest path, 18 September 2026

Agent **RED-TEAM**. Read-only against production `dsvuoovivysszdoiorch`
(`SELECT` and one `STABLE` function call, no write, no DDL, no migration).
Attacks were executed against staging `wwspuxrbiyagnrnzgate`, every one of them
inside a transaction that was **rolled back**. Another agent was writing to
staging at the same time; nothing in this file edits that agent's objects, and
where staging and production disagree it is said so explicitly.

> **The premise this file was written against.** `service_role` has
> `rolbypassrls = true` on both boxes. Every n8n workflow and every webhook
> receiver holds that key. So RLS constrains the browser and constrains
> **nothing** on the ingest path. The only thing standing between one
> dealership's customer and another dealership's database is whether a receiver
> resolves the right tenant — and, where it does not, whether a constraint or a
> trigger catches it afterwards. This file tests both halves.

## 2 · Findings, ranked by what bites first

### P0-1 · The WAHA door is open and writes into quarantine — **severity: critical**

`/webhook/whatsapp-inbound` is live and its auth gate has never been armed.
`ops/n8n-waha-gate/README.md` records the state in its own headline: *"Status,
8 September 2026: still open"* — `WAHA_WEBHOOK_ENFORCE` is not `true`, the gate
reads `mode MONITOR, header_present true, ok false` on real traffic, and
**MONITOR passes everything**. A real customer (lead 122, a real UAE number)
already entered production through it.

Because the workflow names no tenant, every row it writes takes the column
default. Measured on production today:

- `nexus_default_tenant_id()` → **`__unattributed__`** (the quarantine tenant).
- **16** columns in `public` still carry that default.
- **4** `communication_logs` rows and **20** `audit_log` rows are already sitting
  in the quarantine tenant — real customer content, filed outside the dealership
  it belongs to, where `customer`-table RLS does not reach it.

This is not quarantine-and-refuse. It is quarantine-and-carry-on: the bot
answers the customer, spends model budget and writes records, and the dealership
cannot see any of it. With a second dealership it becomes a straight
cross-tenant merge — both dealers' traffic in one bucket.

**Smallest fix.** Two things, in order: (a) resolve the header mismatch and set
`WAHA_WEBHOOK_ENFORCE=true` — the runbook's own step 4; (b) import the tenant
resolution that is already written and has never run. `ops/tenant-scope-bdc/
whatsapp_bdc_ai_agent.TENANT_SCOPED.json` resolves `body.session` through
`channel_registry` and **throws** `BDC_WAHA_SESSION_NOT_REGISTERED` on zero rows
rather than falling through to the default. Its own STATUS.md says it has never
been imported and no node in it has ever executed.

### P0-2 · The older tables take cross-tenant writes; NX995's protection covers only `appointment` — **severity: critical (latent at one dealer, immediate at two)**

NX995 gave `appointment` four composite foreign keys that carry `tenant_id`:
`(tenant_id, customer_id)`, `(tenant_id, lead_id)`, `(tenant_id, assigned_to_id)`,
`(tenant_id, inventory_id)`. **The older tables did not get them.** Confirmed
identical on production and staging.

Proven on staging as `service_role`, rolled back:

```
CROSS_TENANT_CONVERSATION_ACCEPTED
  conversation.tenant_id  = 0b1b…000b   (dealership B)
  its customer.tenant_id  = 0a1a…000a   (dealership A)
  its channel's tenant_id = 52e1…c8ce   (a third dealership)
```

One row, three dealerships, no constraint and no trigger objected.
`conversation_customer_id_fkey` is `FOREIGN KEY (customer_id) REFERENCES
customer(id)` — the plain form — and `conversation` carries no trigger at all.

```
CROSS_TENANT_ASSIGNEE_ACCEPTED
  leads.tenant_id       = 0b1b…000b
  its assignee's tenant = 0a1a…000a
```

`leads_assigned_to_id_fkey` is likewise plain. A lead belonging to one
dealership can be assigned to another dealership's salesperson — and the
escalation and alerting paths key on the assignee.

**What did hold**, and is the template: `lead_event` refused the same attack from
a trigger, not from documentation —

> `ERROR NX001: Lead event belongs to one dealership and cites a lead belonging to another.`
> `DETAIL: LEAD_EVENT_CROSS_TENANT_PROMOTION`

and `whatsapp_record_customer_message` refused a mismatched tenant/integration
pair outright:

> `ERROR 42501: That channel is not an active registered channel of that dealership.`
> `HINT: Resolve the tenant from the channel identity rather than passing both in independently.`

**Smallest fix.** `customer` already has `UNIQUE (tenant_id, id)` and `leads`
already has `UNIQUE (tenant_id, id)`, so both composite FKs can be added without
new indexes:
`alter table conversation add constraint conversation_customer_same_dealership
foreign key (tenant_id, customer_id) references customer(tenant_id, id)`, and the
same shape for `leads.assigned_to_id` against `users(tenant_id, id)`. Note the
hazard recorded in `LEAD-INGESTION.md`: `ALTER TABLE` on `leads` fires
`nexus_guard_born_open_grants()` and has stripped live dashboard write paths once
already this week — so the `leads` half is safer done as a trigger, exactly as
`lead_event_guard_lead_tenant` was.

### P1-1 · Meta hop one verifies every dealership under one box-wide secret — **severity: high, inert today**

`ops/n8n-meta-lead-ads/verify-and-extract.node.js` reads `$env.META_APP_SECRET`
— a single secret for the whole box — and verifies every delivery against it,
whatever `page_id` the body names. Whoever holds that secret can forge a signed
delivery naming **any** Page and be resolved into that Page's dealership. The
WhatsApp Cloud receiver has already moved past this: it fetches a per-dealership
`meta_app_secret` from the vault (NX930) keyed on `phone_number_id`. Meta Lead
Ads has not. Its per-dealer work (NX980) covers the Page **access token**, not
the app secret, and even that has an `env_global_fallback` branch that is **live
by default** — `NEXUS_REQUIRE_PER_DEALER_SECRETS` is unset, so dealer B's lead
would be fetched with dealer A's token. The code says so in its own comment:
*"a fallback nobody ever turns off is how a single-tenant system goes on looking
multi-tenant."*

Inert today only because `lead_ingest_provider_identity` has 0 rows and both Meta
endpoints are `disabled`, so a forged delivery dies at `Page Registered To A
Dealership?` with nothing written.

**Smallest fix.** Set `NEXUS_REQUIRE_PER_DEALER_SECRETS=true` on the box **before**
the first `lead_ingest_provider_identity` row is created, not after. That single
variable removes both fallbacks. Moving the app secret itself into the vault is
the follow-on, and it is the same shape NX930 already shipped.

### P1-2 · What is deployed is not what was audited — **severity: high**

The receivers on the box carry older definitions than the code that passes the

| `JDqy54w2HUH7pHgW` Meta Lead Ads | **active**, updated **2026-09-07** | `ops/n8n-meta-lead-ads/STATUS.md`: hop 1 is on the box; **hop 2 (`fetch-lead-from-graph.node.js`) is NOT on the box**; `meta-lead-ads.workflow.json` **not imported**. 5 GET handshakes, **0 POST deliveries, ever**. |

The Google row is a direct contradiction: something with that name is active on

### P2-1 · 16 columns still default `tenant_id`, so forgetting it is silent — severity: medium

Any `service_role` write that omits `tenant_id` lands in `__unattributed__` and
returns success. There is already customer content there (24 rows across
`communication_logs` and `audit_log`). The default is *safe* — quarantine, not
the wrong dealership — but it is not *loud*. **Fix:** on the tables that a
workflow writes, drop the default and keep `NOT NULL`, so the omission raises
`23502` instead of filing PII somewhere nobody looks.

### P2-2 · Receiver execution data keeps the shared secret — severity: medium

`saveDataSuccessExecution: "all"` on the new receivers means raw bodies persist
in the shared n8n execution store, and a Google delivery carries `google_key` in
its body. The database refuses to store it (`lead_event_payload_carries_no_
shared_secret`) and the node redacts it — n8n keeps it anyway. **Fix:** set
`saveDataSuccessExecution: "none"` on the two lead receivers.

### P2-3 · Staging drift — record it so staging results are not misread

`channel_registry` on **staging** has **zero** foreign keys and **4 of 5** rows
name a `tenant_id` that does not exist in `tenants`. **Production has the FK
(`FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE RESTRICT`) and 0
orphans.** This is harness drift, not a production defect, and it is why
`nexus_resolve_channel_tenant` returns zero rows for most staging channels — the
resolver's `join tenants` finds nothing. Do not read that as a resolver bug.

Both boxes **do** carry `UNIQUE (channel_type, external_identifier)`, so one
phone number or WAHA session maps to exactly one dealership. A land-grab — one
dealer registering a rival's `phone_number_id` first — is possible only for
whoever can write `channel_registry`, which is `service_role` and the onboarding
path, not a webhook caller.

## 3 · Unresolvable mapping: refuse, or fall back?

**The lead-ingest writers refuse, and say why.** Proven on staging as
`service_role`, rolled back:

> `ERROR NX001: No active lead endpoint answers to that key.`
> `DETAIL: LEAD_ENDPOINT_UNRESOLVED`
> `HINT: The endpoint is unregistered, disabled, or its dealership is not active. There is no fallback tenant on purpose: a resolver that guesses is how one dealership's traffic writes another's data.`

**The channel resolver goes silent rather than guessing.**
`nexus_resolve_channel_tenant` is `STABLE SECURITY DEFINER` and joins `tenants`,
requiring `channel_registry.status='active'` **and** `tenants.status='active'`,
with `limit 1` and a predicate that returns nothing at all when the caller's role
is `authenticated` or `anon`. Probed on staging: an unregistered
`phone_number_id` returns **0 rows**; a registered one returns **1**. The
WhatsApp Cloud receiver's false branch then throws rather than continuing —
*"arrived on phone_number_id … which is not in channel_registry under
whatsapp_cloud_phone_number_id. The message was NOT recorded."*

**The exception is the WAHA path, which does neither** — it has no resolver, so
there is nothing to be unresolvable, and the row simply takes the default. That
is P0-1.

## 4 · Replay — and which layer holds it

Two identical deliveries of the same signed event, same
`external_event_id`, **different payload bytes**, both on staging in one rolled-back
transaction:

| delivery | phase | `was_duplicate` |
|---|---|---|
| first | `RECEIVED` | `false` |
| replay | `RECEIVED` | **`true`** |

One row. **No exception** — which is the load-bearing detail, because Google
permanently discards a lead on a 4XX, so a receiver that threw on a redelivery
would throw away real customers.

**The layer is the database, inside the writer.** `nexus_record_lead_event`
catches `lead_event_identity_key UNIQUE (tenant_id, source_key, external_event_id)`
and converts it into a `was_duplicate` flag. It is not in the receiver, and it is
not nowhere. The same shape holds on the WhatsApp path at
`whatsapp_customer_message_seen_pkey`, and `whatsapp_record_customer_message`
refuses a message with no provider id outright (`NEXUS_INBOUND_MESSAGE_ID_
REQUIRED`) rather than minting a per-delivery id that would defeat the key. The
WAHA path dedupes on `processed_messages` PK — whose production PK is
`(tenant_id, message_id)`, so with every dealer writing under the same default
tenant a `message_id` collision between two dealers silently drops a real
message.

## 5 · HMAC: invalid and missing signature

`ops/n8n-whatsapp-cloud/verify-or-refuse.test.js` — **37 assertions, 37 pass**,
re-run today. `ops/n8n-meta-lead-ads/receiver.test.js` — **49 pass**. The
refusals, verbatim from `verify-or-refuse.node.js`:

**Missing** — `401 SIGNATURE_HEADER_MISSING`:
> *"No X-Hub-Signature-256 on the request. Meta always sends one."*

**Invalid** — `401 SIGNATURE_MISMATCH`:
> *"X-Hub-Signature-256 did not match an HMAC-SHA256 of the raw body under the app secret held for this dealership. Either it is the wrong secret or the body was altered."*

**No secret to check against** — `500 NO_APP_SECRET_FOR_THIS_DELIVERY`:
> *"No dealership registered for phone_number_id &lt;id&gt; holds a meta_app_secret. Refusing - this gate is never dormant."*

Named tests that pass: no header → 401; wrong secret → 401; body altered after
signing → 401; `sha1=` prefix refused; truncated digest refused; uppercase hex
refused (Meta sends lowercase); and the gate refuses 500 rather than passing when
no secret exists anywhere, carrying three published HMAC vectors plus a negative
control so a sandbox that computes the wrong digest is caught before go-live and
not during it.

The body is parsed **before** verification, for one purpose only — choosing which
dealership's secret to check under — and the file says why that is safe: a forger
naming someone else's `phone_number_id` has only asked to be verified under a
secret they do not hold.

## 6 · The verdict

**Is a single-tenant controlled launch safe today?**

Yes for the attested paths, **no while `/webhook/whatsapp-inbound` is
unauthenticated.** With one dealership, P0-2's cross-tenant writes have no second
dealership to leak into and the Meta/Google doors are inert because nothing is
registered behind them. What is left biting today is a live, open webhook that
any stranger can POST to, whose output is a bot reply to a real phone number and
a row filed in a tenant nobody owns.

Two things gate a defensible one-dealer launch, and they are hours of work, not
weeks: **arm the WAHA gate**, and **set `NEXUS_REQUIRE_PER_DEALER_SECRETS=true`
before any Meta Page is registered.**

Dealership #2 additionally needs P0-2 closed — the two composite constraints —
and P1-2 resolved, because nobody has read the bytes of the Google receiver that
is running on the box.
