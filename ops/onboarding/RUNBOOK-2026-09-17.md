**Written 17 September 2026.** Every step below was either **REHEARSED** end to end
on staging `wwspuxrbiyagnrnzgate` on 17 Sep 2026, or is marked **NOT REHEARSED**
with the reason. Nothing here is copied from a design document without being run.

**Read `ops/onboarding/BLOCKERS.md` before you run step 1.** Step 0 is a blocking
gate and it is not optional: onboarding dealer #2 is the act that breaks three
production functions for *both* dealerships, including ALBA.

Production is `dsvuoovivysszdoiorch`. Every SQL step below runs as **service_role**
(Supabase SQL Editor). None of these functions are callable by `authenticated`.

Legend: **Ali** = you, at a laptop · **Dealer** = the dealership's own staff in

## 0 · GATE — clear the dealership-#2 silence · Ali · 1–3 days · **NOT REHEARSED (no fix exists to rehearse)**

The failure is rehearsed; the fix is not, because the fix has not been written.

`public.nexus_scoped_tenant_id()` returns a dealership **only while exactly one is
active**. Production has exactly one (`alba-cars`) so it works today. Creating the
second tenant flips it to NULL for every backend caller, and the callers do not
raise — they return nothing.

Measured on staging with 3 active dealerships:

| call | result |
|---|---|
| `nexus_scoped_tenant_id()` | `NULL` |
| `nexus_comm_keys_for_lead('a@b.com','+971500000000')` (2-arg) | `[]` — **no keys** |
| `nexus_comm_keys_for_lead(..., '<tenant uuid>')` (3-arg) | 3 keys returned |
| `search_rag_documents('refund policy', 3)` (2-arg) | `[]` |
| `nexus_tenancy_readiness()` | `BLOCKER — backend scope resolves to no dealership` |

Run on production today, `nexus_tenancy_readiness()` returns **no BLOCKER row** —
because there is one dealership. That is dormancy, not safety.

**Genuine callers that break** (verified by stripping comments from `prosrc`, not
by name-matching): `nexus_comm_keys_for_lead(text,text)`,
`nexus_lead_for_comm_key(text)`, `search_rag_documents(text,int)`, plus the
Customer-360 nightly batch and `v_customer_directory` / `v_inventory_sales` for
`service_role` per the readiness detail.

**Good news, measured:** `nexus_resolve_channel_tenant()` — the inbound WhatsApp
tenant resolver — does **not** call `nexus_scoped_tenant_id()`. Its name appears in
`nexus_multi_tenant_blockers()` only because that function matches on source text
including comments. Verified on staging at 3 tenants: it still resolved the new
dealer's `phone_number_id` to the right tenant.

**Exit check:** `select * from public.nexus_tenancy_readiness();` on a database
with ≥2 active dealerships returns no `BLOCKER` row.

**Rollback:** n/a — this is a code change, reverted by its own migration.

## 2 · Create the tenant, staff row and owner membership · Ali · 1 min · **REHEARSED — PASSED**

```sql
select public.nexus_onboard_dealership(
  'dubai-motors',                         -- p_slug   (globally unique, lowercased)
  'Dubai Motors LLC',                     -- p_name
  'owner@dubaimotors.ae',                 -- p_owner_email (must match auth.users)
  'owner');                               -- p_owner_role (default 'owner')
```

Returns the new `tenants.id`. One call does three inserts: `public.tenants`,
`public.users` (the staff-directory row, unique per `(tenant_id, email)`), and
`public.tenant_members`. It is idempotent on re-run and it **refuses the
quarantine tenant by name**.

Rehearsed on staging: returned `52e10fb2-8067-4f23-b1a5-d35ad613c8ce`.

**Rollback:** **you cannot delete the tenant row.** 35 tables carry an
`ON DELETE RESTRICT` FK to `tenants(id)` (`leads`, `users`, `channel_registry`,
`lead_ingest_endpoint`, `audit_log`, …). The real rollback is:

```sql
update public.tenants set status = 'suspended' where slug = 'dubai-motors';
```

**REHEARSED — PASSED.** With the tenant suspended: the owner's session saw
**0 leads and 0 tenants**, and `nexus_resolve_channel_tenant()` returned **0 rows**
for their number — every channel off the air from one column. Restoring
`status='active'` brought it all back.

## 3 · Add the dealer's other staff · Ali (invite) + Auto (claim) · 2 min · **REHEARSED — PASSED**

```sql
insert into public.tenant_member_invite (tenant_id, email, role)
values ('<tenant uuid>', 'rep@dubaimotors.ae', 'sales');
```

Then invite that same email in Supabase Auth. The trigger
`trg_nexus_claim_pending_membership` on `auth.users` creates the
`tenant_members` row automatically on first sign-in, marks the invite claimed,
and writes an `audit_log` row. It **never overwrites an existing membership**, and
it swallows its own errors so a failure here can never block account creation.

Rehearsed on staging: invite for `zz-rep@dubaimotors.invalid` with role `sales` →
membership row auto-created with role `sales`, `claimed_at` set,
`claimed_auth_user_id` correct. **No manual `tenant_members` insert is needed.**

**Rollback:** `update public.tenant_member_invite set revoked_at = now() where …`
for an unclaimed invite; `delete from public.tenant_members where …` for a claimed
one (no RESTRICT FK blocks this).

## 5 · Register the WhatsApp Cloud channel · Ali · 1 min · **REHEARSED — PASSED**

Prefer the function over the raw insert shown in the older runbook — it validates
the tenant and refuses to steal another dealership's number.

```sql
select public.nexus_register_channel(
  'dubai-motors',                        -- p_tenant_slug
  'whatsapp_cloud_phone_number_id',      -- p_channel_type
  '<their phone_number_id>',             -- p_external_identifier (the REAL one)

```

```
1306545252542419) is already bound to a different dealership. Re-pointing a live
identifier is refused. Delete the existing row deliberately if that is really what
is intended.
```

**Rollback:** `update public.channel_registry set status='disabled' where
integration_id = '<id>';` — `nexus_resolve_channel_tenant()` requires

## 6 · Install the dealer's three credentials · Dealer pastes, Ali runs · 5 min · **NOT REHEARSED (function absent from staging)**

```sql
select * from public.nexus_channel_secret_put('<integration_id>', 'meta_app_secret',        '<they paste>', 'onboarding');
select * from public.nexus_channel_secret_put('<integration_id>', 'meta_system_user_token', '<they paste>', 'onboarding');
select * from public.nexus_channel_secret_put('<integration_id>', 'meta_verify_token',      '<they paste>', 'onboarding');
```

Signature confirmed on production:
`nexus_channel_secret_put(p_integration_id uuid, p_kind text, p_secret text, p_installed_by text)`, `SECURITY DEFINER`.
The three valid `kind` values come from `public.channel_secret_kind` and are exactly
`meta_app_secret`, `meta_verify_token`, `meta_system_user_token`.

Each call returns an 8-character fingerprint. Write those down; they are how you
confirm the right credential is installed without anyone looking at it again.

**Why NOT REHEARSED:** staging has **no `channel_secret` table and no
`nexus_channel_secret_put` function**. Rehearsal attempt returned:

```
ERROR: 42883: function public.nexus_channel_secret_put(unknown, unknown, unknown, unknown) does not exist
```

**And it has never been run in production either.** On production right now:
`select count(*) from public.channel_secret` = **0**, and
`nexus_meta_onboarding_status()` reports all three credentials **`MISSING`** for
ALBA's own number. ALBA's `channel_registry.credential_ref` still reads
`env:META_APP_SECRET+META_WA_TOKEN`. This path is built and zero times used.

**Rollback:** re-run `nexus_channel_secret_put` with a rotated value (it records
`rotated_at`). There is no tested delete path.

## 9 · Lead-ingest endpoints the dealer can use on day one · Ali · 3 min · **REHEARSED — PASSED**

There is **no helper function** for this — it is a raw insert, and the table is
heavily constrained. The two that need no Meta/Google asset at all:

```sql
insert into public.lead_ingest_endpoint
 (tenant_id, source_key, required_provenance_for_source, declared_provenance,
  provenance_counts_as_real, environment, public_key, secret_ref, origin_allowlist,
  ingest_address, status, label)
values
 ('<tenant uuid>','walk_in','operator_recorded','operator_recorded',true,
  'production','dubai-motors-walkin-showroom-floor',null,'{}',
  'dashboard://lead-drawer','active','Dubai Motors - showroom walk-in, recorded by a salesperson'),
 ('<tenant uuid>','phone_call','operator_recorded','operator_recorded',true,
  'production','dubai-motors-phonecall-front-desk',null,'{}',
  'dashboard://lead-drawer','active','Dubai Motors - inbound phone enquiry, recorded by a salesperson');
```

Constraints that will bite you, all verified on production:
- `public_key` must match `^[A-Za-z0-9_-]{24,128}$` and is **globally unique**.
- `environment='production'` forces `declared_provenance = required_provenance_for_source`
  and `provenance_counts_as_real = true`.
- `declared_provenance='operator_recorded'` forces `secret_ref IS NULL` **and** an
  empty `origin_allowlist`.
- `hmac_sha256_x_hub` / `shared_secret_in_body` endpoints **require** a non-blank
  `secret_ref`, and `(source_key, required_provenance_for_source)` is an FK into
  `lead_source_catalogue` — you cannot invent a source key.

Rehearsed on staging: both rows inserted first time.

**Rollback:** `update public.lead_ingest_endpoint set status='disabled' where
endpoint_id = …`. Deletion is blocked by `ON DELETE RESTRICT` from
`lead_ingest_provider_identity` once identities exist.

## 11 · Isolation proof — run this before you hand over a login · Ali · 2 min · **REHEARSED — PASSED both directions**

```sql
-- as service_role, in the SQL editor
select set_config('request.jwt.claims',
  '{"sub":"<their auth_user_id>","role":"authenticated"}', true);
set local role authenticated;
select (select coalesce(json_agg(slug),'[]'::json) from public.tenants)     as tenants_visible,
       (select count(*) from public.leads)                                   as leads_visible,
       (select count(*) from public.channel_registry)                        as channels_visible;
reset role;
```

Rehearsed on staging:
- New dealer's owner saw **1 tenant** (`zz-dubai-motors`), **1 lead** (their own),
  **1 channel** (their own). Tenant A's and B's 4 leads were invisible.
- Tenant A's owner saw **1 tenant**, **2 leads** (their own), and
  `count(*) where tenant_id = <new dealer>` = **0**.

The lock is `public.nexus_current_tenant_ids()`, which returns `tenant_members`
rows joined to `tenants` where `status='active'` and `auth.uid()` matches. RLS on
`leads`, `tenants`, `channel_registry` all key off it; `lead_ingest_endpoint`
denies `anon` and `authenticated` outright.

Note: `authenticated` holds **SELECT only** on `leads`. All writes go through
`service_role`, so the dashboard's write path is a backend concern, not an RLS one.

## What this runbook deliberately does not claim

- No step here was executed against production. Production was read-only throughout.
- Steps 2, 3, 5, 9, 11 and the step-2 rollback were rehearsed against the **real
  functions** on staging and passed.
- Steps 0, 1, 4, 6, 7, 8, 10, 12 were **not** rehearsed, each for the stated reason.

  `channel_secret`, `channel_secret_kind`, `lead_ingest_secret`,
  `lead_ingest_secret_kind` and the five `nexus_*secret*` / status functions. A
  rehearsal on staging therefore cannot cover the credential half of onboarding.
