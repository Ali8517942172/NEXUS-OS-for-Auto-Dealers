lead-ingestion family was promoted to production and the central claim of the
first version of this note stopped being true. Measured against both live
projects, not inferred.

## What changed on 7 September: the ingestion layer is on production

**The earlier version of this note said the `leadingest_*` migrations were
deliberately staged-and-not-promoted, and that the repo was intentionally ahead
of production. That is no longer true and should not be quoted.** All seven are
now applied to production, promoted once the Lead Sources screen became a real
consumer — which was the condition the earlier note set for promoting them.

Two of the seven exist because the rehearsal did its job. `leadingest_06` split
`counts_as_real` in two after it turned out one flag was answering both "did an
external system attest this?" and "is this real business?", which made a
production walk-in endpoint *a row that could not be written* — the ingestion
layer could record Facebook but not the largest source in a UAE showroom.
`leadingest_07` is the same defect one level up, and it reached a customer:
within minutes of the merge the Lead Sources screen showed eight of nine
sources as "Connected" when no receiver existed anywhere and
`lead_ingest_endpoint` held zero rows on both projects. The screen was
rendering `integration_status = AVAILABLE` — a commercial fact about the
provider — as an operational claim about this dealership's wiring. Connection
state is now computed in `nexus_lead_source_readiness()` rather than inferred
by a screen.

## The proofs

Re-run in full on 7 September against production. Digests are over production's
295 rows and the repo's 295 files.

**Version-level rollup — does NOT match, and this is expected.**

```
production   62b553f6e379d9f4f3fcb18894132478
repo         0e4875b733c04305ca3f55a490e562e7      MISMATCH
```

The cause is entirely the minted timestamps above: six repo filenames carry
staging's version for a migration production recorded under a different one.
Six repo versions appear in no production row and six production versions have
no repo file. Nothing is missing on either side and no body differs.

**Body-level rollup keyed by version — also does NOT match, for the same
reason and no other.**

```
production   f627ea3f76302845205afe723286ccf6
repo         8b8f8330288e94f1ada14b24657e9f78      MISMATCH
```

This is worth stating explicitly so nobody reads it as a content failure: the
key of each line is `version:md5(body)`, so a differing version changes the
digest even when the body is byte-identical. Once versions diverge, this rollup
can no longer answer the content question and must not be used for it.

**Body-level rollup keyed by name — MATCHES. This is the one that carries the
weight.**

```
production   fc541447510cfde0aa961df087498d58
repo         fc541447510cfde0aa961df087498d58      MATCH
```

Keyed `name:md5(body)`, ordered byte-wise (`collate "C"` on the database side,
`LC_ALL=C sort` locally), over 295 names that are distinct on both sides. The
name list alone also matches (`f74fcd0c9da6842c551013093b45e341`). So every one
of the 295 migrations in this folder is byte-for-byte what production applied,
under the same name, and the only disagreement anywhere is the version column.

**The 288 shared non-`leadingest` migrations still match on both rollups**,
unchanged from 6 September — `f0c0c12c90394192d8c8cb6a2f314c11` (version) and
`a8f5f33b33130b3fffc4b10e1a4ffd7f` (body by version) on both sides. The
divergence is confined to the seven-file family.

### One measurement trap, recorded because it nearly produced a false alarm

The name-keyed rollup was first computed with Postgres ordering by its default
collation and the local side ordering byte-wise. The digests differed, which
looks exactly like corrupted content. It was a **sort-order artifact**: the same
295 lines in two different orders. Forcing `collate "C"` on the database side
made both sides agree. Any future cross-side digest must pin the collation
explicitly — an ordering difference and a content difference are
indistinguishable in a rollup, and the alarming one is the wrong default guess.

## Open item: the six filenames should be renamed to production's versions

Not done in this pass, because renaming six files is a larger change than the
extraction it would ride along with, and it is a call worth making deliberately.
Recording it here so it is not discovered by accident.

`supabase/migrations/` is defined as one file per row of **production's**
history, named `<version>_<name>.sql`, and `tools/extract-migrations.mjs` keys
files by the 14-digit version. Run against production today it would treat
production's six `leadingest` versions as new, write six additional files, and
report the six staging-versioned files as orphaned `EXTRA` — leaving thirteen
files for seven migrations, six of them duplicates under versions production
has never recorded. `supabase db push` against a fresh project would replay the
family twice for the same reason.

The fix is a rename, content untouched, e.g.
`20260906201008_leadingest_01_… .sql` → `20260907023137_leadingest_01_… .sql`
for each of the six, per the table above. After it, both version-level rollups
match again and this note's mismatch section can be retired.

## How to check this again

```bash
NEXUS_DB_URL=postgres://…  node supabase/tools/extract-migrations.mjs --check
```

It writes nothing and exits 1 when the folder and the database disagree.
Pointed at production **today it will fail**, reporting six missing versions and
six `EXTRA` files — that is the open item above, not new drift. After the
rename it should report nothing at all. `QUALITY_GATE.mjs` asks the same
question as `L11`.
