# Repo ↔ database parity, 6 September 2026

Measured today, against both live projects.

## The counts

`supabase/migrations/` holds **294** files. Production
(`dsvuoovivysszdoiorch`) records **288** rows in
`supabase_migrations.schema_migrations`, head `20260906194609`. Staging
(`wwspuxrbiyagnrnzgate`) records **144**, head `20260906210112`.

Staging's much smaller number is not drift and is not a gap in anything: that
project was stood up from `supabase/baseline/` rather than by replaying the
whole recorded chain, so its history table begins where the baseline begins.
Its count is not comparable with production's and should not be read as one.

## The only remaining difference: six `leadingest_*`, staged and not promoted

Six migrations are applied to **staging only**, and are deliberately **not**
promoted to production:

| version | name |
|---|---|
| `20260906201008` | `leadingest_01_provenance_and_source_vocabulary` |
| `20260906201107` | `leadingest_02_tenant_bound_endpoints` |
| `20260906201224` | `leadingest_03_the_lead_event` |
| `20260906201355` | `leadingest_04_writers_and_the_dealer_projection` |
| `20260906201743` | `leadingest_05_the_dealer_read_path_and_the_secret_in_the_payload` |
| `20260906210112` | `leadingest_06_a_walk_in_is_real_business_it_is_just_not_attested` |

All six were extracted byte-exact from staging. Each file's md5 and octet
length match what Postgres reported for `statements[1]`, and none carries a
trailing newline — the same form `tools/extract-migrations.mjs` writes.

The sixth is a correction to the first five rather than new surface, and it is
the argument for rehearsing on staging in miniature: `counts_as_real` was doing
two jobs at once, so a production `walk_in` or `phone_call` endpoint was a row
that could not exist — the ingestion layer could record Facebook but not the
largest source in a UAE showroom. Splitting the commercial question from the
attestation question fixed it. Had the five gone straight to production, that
defect would have gone with them.

**So the repo↔production fingerprint this project normally holds is
intentionally six files ahead, and that is now the whole of the difference.**
The reason is that the ingestion layer has no consumer yet: nothing calls
`nexus_record_lead_event`, nothing resolves an endpoint by public key, and no
workflow writes a `lead_event` row. It is being rehearsed on staging first, and
promoting a lead-ingestion layer to production before anything reads or writes
it would put six migrations of new surface — new tables, new RLS, a new
dealer-facing view — in front of paying customers to no purpose. When a
consumer exists, these six go to production in version order and the counts
converge again.

Earlier today this folder was also two migrations **behind** production. Both
had been applied through the MCP tool, which writes a history row and writes

been extracted from production, which is the source of truth for them, and

The gap existed for roughly an hour of working time and was found by counting

## The proof, at two strengths

Re-run in full after the sixth `leadingest_*` was added, not carried over.

**Versions.** `md5` over production's 288 versions, newline-joined in version
order, is `f0c0c12c90394192d8c8cb6a2f314c11`. The same digest computed locally
over the repo's 294 filenames with the six `leadingest_*` removed gives the
identical value, over 288 versions on both sides. So no file is missing on
either side and no third discrepancy hides behind the counts.

**Bodies.** Matching filenames would not prove the contents match, so the
stronger check was run too — `md5` over `version:md5(body)` lines in version
order, newline-joined with no trailing newline, which is the rollup
`supabase/README.md` already uses:

```
production   a8f5f33b33130b3fffc4b10e1a4ffd7f
repo (288)   a8f5f33b33130b3fffc4b10e1a4ffd7f
```

Identical. Every one of the 288 files this repo shares with production is
byte-for-byte what production applied — not merely present under the right
name.

## How to check this again

The repo's own check, which compares bodies and not just counts:

```bash
NEXUS_DB_URL=postgres://…  node supabase/tools/extract-migrations.mjs --check
```

It writes nothing and exits 1 when the folder and the database disagree.
Pointed at production it should now report only the six `leadingest_*` as
`EXTRA` — the expected answer for the reason above — and nothing missing.
`QUALITY_GATE.mjs` asks the same question as `L11`.
