## 2 · Item 3 in full — the idempotency family

The audit left four open. Measured from the catalogue tonight rather than
believed:

- **`policy_applied_rule_id` foreign key** — closed (item 4).
- **`integration_id` in the delivery-events key** — closed (item 5).
- **The eight composite tenant/carrier foreign keys** — closed. Measured: **8**
  foreign keys reference `channel_registry(integration_id, tenant_id)`. A
  status callback can no longer be filed under one dealership while naming
  another dealership's carrier.
- **`communication_logs`' inert unique index** — **the database half is closed
  and the defect is not.** `2e6b238` and `9146fe4` replaced the index with
  `communication_logs_external_identity_key` over
  `(tenant_id, channel, direction, external_message_id)`, with `channel` and
  `direction` entering through generated, unwritable normalised columns. It is
  still inert in practice: measured today, **114 rows, 0 of them carrying an
  `external_message_id`**. Every writer is an n8n node, all `retryOnFail`, none
  sending the column, and **the box was not touched**. The change is written up
  in `ops/evidence/communication-logs-writer-change-NOT-DEPLOYED.md`.

Three more were found by looking deliberately and closed (`2e6b238`):
`processed_messages.message_id`, `whatsapp_customer_message_seen` /
`channel_message_events` / `whatsapp_delivery_events` (all three previously
accepted any trimmed non-empty string), and `whatsapp_templates` language and
WABA identity. A CHECK now refuses ids minted per attempt — `nokey:`,
`outreach:`, `exec-`, `run-`, `job-`, bare 10- and 13-digit epochs. `CLAUDE.md`
records `whatsapp_customer_message_seen` as "defeated by the live `nokey:`
shape"; **it is not defeatable that way now.**

**Open, and stated rather than papered over:**

- The reply-duplication defect itself needs the n8n node change in
  `ops/evidence/n8n-processed-messages-nokey-NOT-DEPLOYED.md`. `Claim
  Message Id` is `onError:continueRegularOutput` and `Is New Message?` is an OR
  that includes `!!$json.error`, so the path is **fail-open** and the constraint
  does not stop a duplicate reply. What it stops is the table recording a false
  idempotency claim.
- `processed_messages` has no `integration_id`, and adding one would break the
  live inbound path.
- The master router still posts `leads?on_conflict=email` against a
  `(tenant_id, email)` index.
- A SEND citing a decision from a *different conversation* still cannot be
  refused by a constraint, because no decision entity is persisted.

## 3 · Two places the audit was wrong

Both were proved wrong by work done tonight, and both are corrections *against*
the audit rather than softenings of it.

**The inventory DELETE did not fail on a control.** The audit recorded a delete
attempt as refused. `eb29fbb` measured the refusal: it was `23503`, a foreign
key from `inventory_actions` — **an incidental lock, not a control.** A unit
with no action history deleted cleanly. This is the same shape `CLAUDE.md`
warns about at length: when you record which lock stopped a verb, name the real
one, and if it is incidental treat the object as open. The audit's *conclusion*
— that `inventory` and `leads` had no role model — was right; its *evidence* for
one line of it was not.

**The KYC decision nodes exist.** The audit read `APPROVED 0 / REJECTED 0 /
ESCALATED 0` on Compliance and concluded that no KYC decision endpoint exists.
`87ae4a0` found the Record KYC nodes in the auditor workflow at
`kyc_aml_..._phase_5.json:448` and `:493`. **The endpoint is missing from the
dashboard, not from the system.** The screen now prints an em dash with "Not
zero — nothing to count", gated on all three verdicts summing, so it
self-cancels the moment the register is demonstrably written. The audit's
underlying finding — a capability gap rendered as a measured zero — was correct
and is now fixed; its attribution of the gap was not.

## 4 · What else closed tonight that the audit listed as open

### The role model on `inventory` and `leads` — closed at the database, half-shipped at the screen

The audit: *"`inventory` and `leads` grant ALL to every tenant member … a junior
rep can permanently delete a vehicle."* Closed by `eb29fbb` (five migrations,
`rbac_01`…`rbac_05`) and the dashboard half by `2765f28`.

`tenant_members.role` is extended rather than a second model invented:
`owner | admin | manager | sales | technician | member`, with `member` — the
column default — moving from ceiling to floor. Verified in production today:
the CHECK carries exactly that vocabulary, six RESTRICTIVE policies sit on the
two tables, and the `inventory_guard_cost_change` trigger exists.

Three mechanisms, and **which lock stops what is stated exactly**, because that
distinction is the reason this section exists at all:

| refusal | the lock | what you see |
|---|---|---|
| any role writing a derived or machine-owned column (`ai_score`, `gross_margin`, `days_in_stock`, …) | column GRANT | `42501` |
| sales / technician / member touching an inventory row | RESTRICTIVE RLS | **0 rows**, not an error |
| sales touching another rep's lead | RLS `USING` | 0 rows |
| sales giving away their own lead | RLS `WITH CHECK` | `42501` |
| manager inserting a vehicle | RLS `WITH CHECK` | `42501` |
| anyone below owner **moving** the cost price | BEFORE UPDATE trigger | `NX001` |

Measured privilege state today: no table in `public` grants `authenticated` a
table-level UPDATE. `inventory` is `authenticated=rd`; `leads` is
`authenticated=r`. **`relacl` alone is now a misleading witness on both tables,
in both directions** — `leads` reads "read-only" while eight columns are
writable through `pg_attribute.attacl`, and `inventory` reads `rd` while the
real lock on `cost_aed` is the trigger, not the ACL. Anyone re-running the ACL
query in `CLAUDE.md` must read column ACLs too.

**Not closed, and it is a judgement call rather than an oversight.** `rbac_02`
withheld `UPDATE(cost_aed)` outright, which is the stronger lock, and it is
**not** what shipped. The deployed bundle's `unitRow()` sends `cost_aed` on
every save, so the outright withhold would return `42501` on every "Save
changes" for the only live user. `rbac_05` restores the grant and moves the rule
to the trigger. **Re-apply `rbac_02`'s two statements in the same release as the
rebuilt dashboard.**

**And the model is inert today.** Production holds exactly one login, the
owner's, already `role='owner'`. There is no UI to add a colleague. What needs
review is the *next* login: it inherits `member`, which now means
own-leads-only.

### `workflow_registry` — narrowed, not closed

The audit: *"18 rows of workflow ids and cron expressions, `SELECT USING (true)`,
no `tenant_id`."* `edf001d` took the columns off the dealer plane. Measured
today, `authenticated` reads **7 of 10** columns:
`name, audit_name, category, is_active, description, writes_audit_log,
audit_aliases`. **`id`, `trigger_type` and `trigger_detail` are withheld** and
return `42501`.

**Still open, and deliberately red.** There is no `tenant_id` and the policy is
still `USING (true)`, so a dealership can still learn *which* automations exist
and which are switched off — `count(*)` reads no column. Gate check **L2** fails
on exactly this row and `workflow_registry` is still not in `L2_EXEMPT_TABLES`.

The follow-on defect is worth recording because it is the shape this project
keeps hitting: withholding the columns left the dashboard telling a falsehood.
Four paths in `automation.js` told the dealership that no workflow records a
cadence and that entering one would turn the panel on. `87ae4a0` fixed it with
`triggerReadable()`, which tests key **presence** rather than truthiness, so
"the column was withheld", "the register recorded nothing" and "the view
returned nothing" stay three different findings.

### The gate now checks that a mechanism *works*

`6870cd2`. `L3` asked whether `reloptions` contained the string
`security_invoker` — so a view created with `(security_invoker = false)` passed
the check that exists to forbid it. It now parses the value, and accepts

function text; `L2` arm 2 detects an open policy by the literal string `true`,
