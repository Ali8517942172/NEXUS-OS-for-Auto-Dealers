# NEXUS OS — production readiness audit

4 September 2026. Three independent agents measured the live systems: the
database, the shipped dashboard, and the n8n box. **Every number below came
from a statement executed today** — nothing is quoted from this repo's own
documents, several of which turned out to be wrong.

---

## The verdict

**NEXUS is not production ready, and the gap is narrower than it looks in one
place and wider in another.**

The database is in good shape. The dashboard does what the product promises,
measurably, on live screens. **The messaging layer — the thing four agents
built over two days — has never carried a single message and nothing calls
it.** On the n8n box, **two of twelve** conditions for switching WhatsApp on
are true, and the one that is true is a control nobody built for that purpose.

One finding outranks the rest commercially: **the entire product
differentiator lives on an unmerged branch.** `origin/main` has 14 screens and
no Revenue Recovery group at all. A rebuild from main today ships a dashboard
with the Action Center, the five revenue engines and the honesty machinery
removed.

## Backend — the strongest part

59 tables, 39 views (**all 39 carry `security_invoker`**), 262 functions, 159
policies, 359 constraints, 168 indexes. RLS enabled on 59 of 59.

**Privilege posture is now genuinely closed for `anon`:**

| role | schema USAGE | tables readable | tables writable |
|---|---|---|---|
| `anon` | **false** | **0** | **0** |
| `authenticated` | true | 43 of 59 | **2** |
| `service_role` | true | 59 | 59 |

The only two objects `authenticated` can write are `inventory` and `leads` —
the two deliberate dashboard paths. No TRUNCATE anywhere. Seven column-level
grants, all on `channel_registry`, with `credential_ref` correctly withheld.

**The live endpoint agrees with the ACL**, which has not always been true here:
seven REST paths return `401 / 42501 permission denied for schema public` on
both the publishable key and the legacy anon JWT.

### Still open in the database

- **`whatsapp_delivery_events` keys on unnormalised `status_raw`** — `delivered`
  and `DELIVERED` both inserted, two rows for one status. And the key omits
  `integration_id`, so a second integration's real delivery report is refused
  and dropped.
- **Eight of nine tables carrying both `tenant_id` and `integration_id` accept
  a mismatched pairing.** Only `channel_send_directive` has the composite
  foreign key. The functions check; the tables do not; and n8n writes tables
  directly as `service_role`.
- **`policy_applied_rule_id` is a bare uuid with no foreign key** — a SEND can
  cite a rule that exists nowhere. One constraint fixes it.
- **`communication_logs`' unique index is inert** — all 108 live rows have
  `external_message_id` NULL, and no writer sends the column.
- **`workflow_registry`** — `SELECT USING (true)` for `authenticated`, no
  `tenant_id`, 18 rows of workflow ids and cron expressions.
- **`is_unattributed_default` still points at ALBA CARS**, so a second
  dealership's traffic would file under it.

## The messaging layer has never been used

Every operational table is at **zero live rows**: `whatsapp_opt_in_event`,
`whatsapp_delivery_events`, `whatsapp_message_usage`, `whatsapp_templates`,
`channel_message_events`, `tenant_capability`, `policy_platform_attestation`
have **never held a committed row**.

`channel_registry` holds exactly one row — the WAHA session. **There is no
Cloud API row at all.**

And on the box: **zero calls** to `channel_registry`,
`nexus_resolve_channel_tenant`, `whatsapp_policy_decision_for_channel`,
`nexus_request_send`, `whatsapp_record_customer_message` or
`whatsapp_record_opt_in_event` in any published workflow. The seven
occurrences of `policy_rule` are all comments.

**Wired to nothing, confirmed from both sides.**

## Frontend — the product's promise holds

All 20 screens render live. **Zero console messages, zero failed network
requests** across a full walk.

**The central commercial claim was tested and it holds.** Revenue Recovery
renders the three words as three separate derivations:

- **Estimated → "Not computed"**, not zero — *"no lead carries a budget and
  nothing links a lead to a unit"*
- **Attributed → AED 0**, with the reason
- **Confirmed → AED 585,000** — *"This money is on the books and none of it is
  attributed to anything NEXUS did"*

And it refuses the aggregate: *"There is no total 'revenue at risk' on this
page, and there is not going to be one."*

Under a **forced 403**, a tile rendered `—` and said *"could not be read …
nothing is claimed here and nothing is ruled out"*. It did not manufacture a
plausible zero. That is the behaviour the whole product rests on, and it works.

**One defect:** `compliance.js:1328-1341` renders three bare zeros —
`APPROVED`, `REJECTED`, `ESCALATED` — with no caption. And no KYC decision
endpoint exists, so `APPROVED 0` can never become non-zero. **A capability gap
rendered as a measured zero**, which is exactly what PRODUCT.md forbids.

### Two frontend findings that matter more

**The vendor boundary is fully open**, exactly as `CONTROL-PLANE.md` predicted,
plus five leaks it missed. Live on the signed-in site: *"one n8n instance
serves every dealership"*; the VM's bare public IP **nine times** on Settings;
`Execution <id>` **129 times** on Automation; raw n8n errors; the supplier
chip list. The widest one the document missed is **`lib/states.js:8`, which
renders the raw backend error verbatim across 15 screens** — proved live, a
dealership was shown `403 Forbidden — permission denied for view`.

**`inventory` and `leads` grant ALL to every tenant member.** `polcmd = '*'`,
no staff-role separation. A junior rep can permanently **delete a vehicle**
through the unit form, and the button will work. The Action Center has a
careful authority model; the two tables underneath it have none.

**The dealership's-customer surface is 0% built** — no directory, no route, no
build target, and no appointments table.

## The n8n box — two of twelve

21 workflows, **328 nodes measured** (334 including three pages the tool cannot
read). **19 published, 2 not** — and one of those two is **NEXUS Infra Health
Probe**, the alarm that watches the WhatsApp channel. It is unpublished,
inactive, and **has never executed**. Nothing is watching.

**All eleven webhooks carry `authentication: ABSENT`.** Every one accepts the
request and starts an execution before refusing.

**The WAHA gate is DORMANT on today's live traffic** — `mode: DORMANT`,
`header_present: false`. So `WAHA_WEBHOOK_SECRET` is unset, and WAHA is not
sending the header. Arming it today would drop every real message.

**The second sender is still active.** Today, 575 ms apart, same `payload.id`:
one from `35.224.126.225` (the box) running WAHA 2026.7.2, one from
`2.50.10.149` (external, UAE) running 2026.7.1, different device index on the
same WhatsApp account. 317 executions today, roughly 158 distinct messages.

**Later, 8 September 2026 — what that second sender is.** Ali stated it is his
own Windows desktop `desktop-l3an0ma`, running WAHA in Docker Desktop; the same
PC that used to host n8n behind a Tailscale funnel at
`https://desktop-l3an0ma.tail2141f7.ts.net`, from before the move to GCP. That is
the owner's statement, not a measurement taken here, and it does not change any
number above. **What was later measured, and is recorded in the correction
appended at the end of this file:** it had not stopped — execution 11103 on
8 September at 06:07:40 UTC posted `session.status` from `2.50.10.149` with no
secret header — and its containers were stopped by hand at 06:08:24 UTC. Status:
**identified, and stopped by hand on 8 Sep 2026 — not yet permanently removed
(`restart: always` still declared, device 8 still linked)**.

**And a correction that matters commercially:** almost all of that
deduplicated traffic is **Status broadcasts, group messages and marketing
templates** — not customer conversation. The true customer count today is far
below half of 317.

**No successful customer reply in the last 24 hours.** No execution ran longer
than 1.39 s; a real AI reply takes ~18 s. The one genuine inbound was a Tabby
marketing template, correctly declined.

**One control is working and it was not built for this:** `Claim Message Id`
absorbed the duplicate delivery live today — 9554 claimed it, 9553 got `{}` and
took the false branch.

## Where our own documents were wrong

The most useful output of this audit. Six places `CLAUDE.md` disagrees with
measurement:

1. **The `postgres`/`storage` default-ACL line is closed.** The file says
   nobody has looked at it. `anon` appears in neither the table nor the
   sequence line.
2. **Staging parity is achieved.** The file says the `channel_registry` column
   grants are missing there. They are present, with an identical fingerprint.
   **This unblocks rehearsing the tenant-map switch.**
3. **`slack-command` is closed by design now, not by accident.** The file says
   its guard halts before `Auth Gate` runs. Republished 3 Sep 08:54; execution
   9325 proves `Auth Gate` runs and the refusal is recorded as ERROR.
4. **`authenticated` no longer reaches born-open tables.** True when written,
   describing a probe table that no longer exists. What it reaches today is
   149 harmless vector and trigram functions — **zero tables**.
5. **The `external_message_id` gap is twice as wide as recorded** — missing
   from the outbound writer too. The column name appears in **no** published
   workflow anywhere.
6. **"11 Bitrix24 nodes"** names a node type that does not exist on the box.

## The repository is 12 migrations behind, and those 12 are the security work

`supabase_migrations` holds **255**; `supabase/migrations/` holds **243**. The
twelve missing files are the entire 4 September hardening set — the consent

**A rebuild from this repository today reproduces the born-open grants, the
open schema door and the pre-fix consent identity.** This is the only item on
the list where the *record* rather than the *system* is wrong, and it is
mechanical to fix.

# CORRECTION APPENDED — 8 September 2026: `2.50.10.149` had not stopped

**Nothing in the body of this document is rewritten. No number in it is
re-derived.** This section records a later measurement that makes one claim
carried in this file — and repeated across the repo — false, and states the
corrected status.

**The measurement.** Production n8n execution **11103**, **8 September 2026 at
06:07:40 UTC**:

```
x-forwarded-for            2.50.10.149
user-agent                 WAHA/2026.7.1
me.jid                     971526647253:8@s.whatsapp.net
body.environment.version   2026.7.1
body.event                 session.status
x-nexus-webhook-secret     absent   ->  _gate.header_present = false
```

`2.50.10.149` was **still posting into `/webhook/whatsapp-inbound` on production
on 8 September**, two days after this repo recorded it as gone.

**Why the 6 and 7 September samples missed it.** Both grouped by `payload.id` and
looked for duplicate pairs. That host's WhatsApp session is no longer
authenticated, so it emits `session.status` events and **no `message` events at
all** — events that carry no `payload.id` and can therefore never form a pair.
**Absence of duplicates is not absence of the sender.**

**What was found and done.** Docker Desktop on Ali's Windows desktop
`desktop-l3an0ma` showed a compose project **`nexus-os`** at
`C:\Users\user\Desktop\MY RESUMES\nexus-os` with **three containers
running**: `n8n` (5678), `n8n-db` (postgres:16-alpine) and `waha`
(devlikeapro/waha, 3000). Its WAHA log at 06:02:22 records a `session.status`
POST to `https://35.224.126.225.nip.io/webhook/whatsapp-inbound` returning 200.
The compose project was **stopped by hand through the Docker Desktop UI at
06:08:24 UTC**. The GCP box was unaffected — `/healthz` `ok`, executions 11104
and 11105 from `35.224.126.225` in the same minute. Deletion was declined,
because the confirmation dialog says nothing about the named volumes that hold
that n8n's workflows and credentials and the WAHA linked-device session.

**Corrected status, replacing every earlier wording in this file:
identified, and stopped by hand on 8 Sep 2026 — not yet permanently removed
(`restart: always` still declared, device 8 still linked).** `restart: always` is
declared on all three services, and Docker restarts a manually stopped `always`
container when the daemon next starts, so a Docker Desktop restart or a Windows
reboot brings it back. The outstanding steps are
`docker update --restart=no n8n n8n-db waha` on that PC and unlinking WhatsApp
device **8** on the handset. Neither has been done.

**And a second, unrelated blocker measured the same day.** The WAHA gate now
reads `mode MONITOR, header_present true, ok false` on the box's own traffic.
The box is in queue mode (`executionMode: "queue"`), so the Code node that reads
`$env.WAHA_WEBHOOK_SECRET` executes in `n8n-worker`, not in `n8n`. Enforcement is
therefore still blocked — for a different reason than the second sender.

Authoritative account: `CLAUDE.md`, sections "It had not stopped. It was stopped,
by hand, at 06:08 UTC on 8 September 2026" and "The worker is the process that
reads `$env`, and the box is in queue mode".
